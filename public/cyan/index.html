A small systems language that stays out of your way.

I am God\'s Chosen Programmer. I was handed a short list, a RISC-V processor, a language, a compiler and an operating system, and told to build all of it. Cyan is the language, the foundation the rest will stand on. Sodium is its compiler, because Cyan is a god and gods have favourites.

function fact(n: i64) -> i64 {
    if (n <= 1) { return 1; }
    return n * fact(n - 1);
}

function main() {
    print("hello, Cyan");
    print("10! is %d", fact(10));

The first commandment

Everything else gets built on top of this, so it has to be right. It has to be small enough that one chosen programmer can hold all of it in their head, and honest enough that nothing is hiding underneath.

Cyan answers to no standard library. A program begins in a tiny _start and speaks to the kernel directly. The allocator, the printer and the float formatter all live in sodium-rt, and I wrote every line of it myself.

There are two altars. x86-64 is for the machine on my desk, and RISC-V 64 is for the processor I was told to build. One source file goes through one register allocator and comes out as two native programs. An IR verifier watches Sodium's own work between every pass, because even a favourite can slip.

When something does go wrong, Cyan can make you pay for it. Pass --bounds, --check-null or --stack-probe and a bad access ends the program with exit status 70 and a clear message. Leave the flags off and you pay nothing, the output is the same as ever.

It still speaks C. Calls follow the usual conventions on both targets, floats and small structs included, and I check them against gcc, so the old world and the new one can keep talking to each other.

Even prophets like their editors to be helpful. There is a language server for errors, completion, hover and go to definition, and a VS Code extension that connects it.

Every example in the README is compiled and run by the tests. If the docs ever stop matching the compiler, the build breaks and I hear about it immediately.

A quick tour

If you have written C, most of this will feel familiar. The differences are small, and they are mostly about removing annoyances.

Types that say their width

Integers are i8 to i64 and u8 to u64. A plain var becomes an i64, and small types promote to i32 just like in C, so nothing sneaks up on you.

You also get bool, char and type aliases.

function main() {
    var a = 5;            // inferred i64
    var b: i32 = 10;      // explicit width
    var c: u8 = 255;
    var flag: bool = true;
    var ch: char = 65;
    print("%d %d %d %d %d", a, b, c, flag, ch);
    return 0;
}

Structs, enums and pointers

Structs are just typed fields. Pass them by pointer or return them by value. Enums are named constants, and you can pick the values yourself.

Pointer arithmetic scales by element size, and malloc and free come from a small allocator built into the runtime.

struct Point { var x: i64; var y: i64; };
enum Color { Red, Green = 5, Blue };

function main() {
    var p: Point;
    p.x = 10;
    p.y = p.x + 5;
    print("%d %d", p.x, p.y);
    print("%d %d %d", Red, Green, Blue);

    var buf = malloc(32);
    *buf = 7;
    *(buf + 8) = 9;
    print("%d", *buf + *(buf + 8));
    free(buf);
    return 0;
}

Floats that match the ABI

f32 and f64 follow the C calling convention on both targets. Printing is handled by the runtime itself, with no libc printf behind it.

Conversions are spelled out with as, so a float never turns into an integer behind your back.

function main() {
    var a: f64 = 7.5;
    var b: f64 = 2.5;
    var c: f32 = 1.5f;
    print("%f %f %f", a + b, a * b, a / b);
    print("%f", c);
    print("%d", (a + b) as i64);
    print("%f", 1e3 + 2.5e-1);
    return 0;
}

A preprocessor and inline assembly

Macros and conditional compilation work the way you expect. When you need a single machine instruction, asm takes the architecture, the line and a clobber list, so one file can carry code for both targets.

#define LIMIT 3
#define DOUBLE(x) ((x) * 2)

function main() {
#if defined(LIMIT) && LIMIT == 3
    var n = DOUBLE(2);
#else
    var n = 0;
#endif
    asm("x86_64", "nop", []);
    asm("riscv64", "nop", []);
    print("%d", n);
    return 0;
}

Safety when you ask for it

The checks are off by default. Switch them on and a bad access stops with exit status 70 and a clear message, instead of a mystery crash three functions later.

$ sodium --bounds --check-null --stack-probe app.cyan
$ ./app
$ echo $?
70

One source, two machines

Pick the target with a flag. Every test runs on both and has to give the same answer, so what works on your laptop also works under qemu on RISC-V.

$ sodium -o myprog program.cyan             # x86-64 is the default
$ ./myprog

$ sodium --target riscv64 program.cyan
$ qemu-riscv64 ./program

$ sodium -S program.cyan                    # stop at assembly
$ sodium -g program.cyan                    # line tables for gdb

Get started

You will need a C++20 compiler, CMake and NASM. If you want to try RISC-V too, add the RISC-V binutils and qemu.

Build the compiler

$ git clone https://github.com/vajradevam/sodium
$ cd sodium
$ cmake -B build -DCMAKE_BUILD_TYPE=Release
$ cmake --build build -j$(nproc)

Write a program

Everything starts in main, and whatever it returns becomes the exit code.

function main() {
    print("hello, Cyan");
    return 0;
}

Compile and run

$ ./build/sodium hello.cyan
$ ./hello
hello, Cyan

Keep it around

This puts sodium on your path and sets up the VS Code extension as well.

$ ./scripts/install.sh --vscode
